## Problem Statement
Order emails currently arrive by email with no owner inside the app. Checking Gmail for new orders is "ad hoc/inconsistent" — no staff member has a clear routine for it. The Emails tab in the app only shows OUTBOUND mail (the `email_log` table — order-created/status-changed/price-assigned notifications sent via Resend). It has no visibility into the INBOUND mailbox where clients actually send orders.

## Demand Evidence
A real incident has already happened: a client discovered their own missed order before staff did — the client noticed the order was never picked up before anyone on staff caught the email. Confirmed as having happened "at least once, concretely," not hypothetical.

## Status Quo
No consistent routine exists. It's not "a specific staff member checks Gmail manually" — it's genuinely ad hoc, meaning any given order email might sit unread for an unknown period depending on who happens to check.

## Target User & Narrowest Wedge
Staff who are already living inside the app via the existing 20-second polling loop (`startPolling()`, index.html:1015-1022) and the always-rendered tab bar. The narrowest wedge is not a new alerting channel — it's making the inbound mailbox visible where staff are already looking, with a low-friction path to act on it.

## Constraints
- Frontend is a single static `index.html` with no build step — no way to hide OAuth secrets from browser devtools. Gmail OAuth client secret + refresh token must live server-side, in a Supabase Edge Function secret, never shipped to the client.
- No existing polling/cron infrastructure in this repo beyond a nightly GitHub Actions `db-backup.yml` workflow. Any Gmail-polling mechanism needs new infra, most naturally a new scheduled GitHub Actions workflow following that same pattern.
- Only two Edge Functions exist today (`admin-create-client`, `send-order-email`), both outbound. This is new inbound surface.

## Premises
- **Challenged and revised during this session:** I initially proposed that the fix needed active alert/toast infrastructure on top of an inbox viewer. The user disagreed, and on reflection was correct — the actual friction isn't "staff don't get notified," it's the **context-switching cost** of leaving the app to log into a separate Gmail account. Staff are already in the app constantly (20s polling, tab bar always visible), so a persistent, ambient signal inside the app they're already in beats an active push notification.
- **Accepted:** Gmail OAuth secrets must live server-side (Supabase Edge Function secret), never in the static client.
- **Accepted:** This repo has no polling/cron infrastructure beyond the nightly backup workflow — new infra is required, and the nightly-backup GitHub Actions workflow is the closest existing precedent to extend.

## Approaches Considered
### Approach A: Badge + manual convert (chosen)
Reform the Emails tab into Sent / Inbox sub-views. A new GitHub Actions cron job (reusing the nightly-backup pattern) hits a new Edge Function every 5-10 minutes. That function polls the Gmail API using a stored OAuth refresh token (Supabase secret) and writes new messages into a new `inbound_emails` table. A persistent unread-count badge appears on the Emails nav tab (visible regardless of which tab is active, since the tab bar always renders). Each inbound row gets a "Convert to order" button that opens the existing manual-order sheet, pre-filled with a client match by sender email and the email body dropped into notes. Attachments (e.g. condition photos) are out of scope for the wedge — the convert action only carries over the email body text.

### Approach B: Full pipeline (rejected — too much for the wedge)
Real-time push (not polling), automated order-detail parsing out of email body, and a full audit trail of who-saw-what-when. More complete, but higher build effort and real parsing-accuracy risk for a problem whose actual root cause is visibility, not automation depth.

### Approach C: Inbound webhook via existing email provider (rejected — wrong shape for the ask)
Route inbound mail through Resend's inbound-webhook support instead of Gmail OAuth, avoiding Google API entirely. Rejected because the user's actual ask and existing client workflow is Gmail-specific (clients already send to a Gmail address staff know); switching providers to sidestep OAuth would require re-pointing where clients send orders, which is a bigger operational change than the OAuth setup it avoids.

## Recommended Approach
Approach A. It matches the actual friction identified during the premise challenge — visibility inside the already-open app, not a new alert channel — and reuses an existing infra pattern (the nightly-backup GitHub Actions cron) instead of introducing new real-time infrastructure the problem doesn't call for.

## Open Questions
- Which mailbox does this poll — a shared support/orders inbox, or an individual's personal Gmail? Affects OAuth consent-screen setup and refresh-token ownership.
- How should inbound sender email be matched to a client record — exact match against the client's on-file email, or fuzzy matching? What happens on no match (walk-in / new-client path)?
- Gmail API rate limits and quota at 5-10 minute polling — confirm this stays well inside free-tier quota.
- What counts as "unread" for the badge — is it the same state as "not yet converted," or a separate read/unread flag independent of conversion? Tied to the next question: does a row disappear or stay listed (read, but present) after "Convert to order"?
- Dedup: poll windows will overlap, so inbound rows need a stable key (Gmail message ID) to avoid re-inserting or re-badging the same email twice.
- Filtering: does every message in the mailbox get a row (spam, unrelated replies, thread noise included), or only some subset (e.g. first message in a thread)? Affects whether the badge count stays meaningful.
- OAuth consent-screen publish status: an unverified/"Testing" Google OAuth app typically expires refresh tokens on a rolling ~7-day basis unless the app is published or the mailbox is a Google Workspace account granted internal-app status. This needs to be confirmed before generating the refresh token in The Assignment below, or polling will silently die a week in with no code change.
- GitHub Actions auto-disables `schedule` triggers on a repo with no commit activity for 60 days. Low risk on an actively-developed repo, but the same "silently dies with no code change" failure mode as the OAuth expiry above — worth a periodic check if commit cadence ever slows.

## Success Criteria
- New inbound order emails are visible inside the app on an eventually-consistent basis (~10 minutes typical) — GitHub Actions `schedule` triggers aren't guaranteed to fire exactly on time, so this is a target cadence, not a hard SLA.
- The unread badge on the Emails nav tab accurately reflects whichever state model is chosen (see Open Questions on unread vs. converted) — this criterion is gated on that question closing.
- No repeat of the demand-evidence incident: a client should never discover their own missed order before staff does.

## Dependencies
- New `inbound_emails` table migration, keyed on Gmail message ID for dedup — per this project's existing pattern, migrations are not auto-applied; this needs a manual apply-and-verify step post-merge, not just a frontend deploy check.
- One-time manual setup outside of code: a Google Cloud project, OAuth consent screen (published or internal-app status — see Open Questions), and a generated refresh token scoped read-only to the target mailbox.

## The Assignment
Go set up the Gmail OAuth side: create a Google Cloud project, configure the OAuth consent screen, and generate a refresh token (readonly scope) for whichever mailbox actually receives client order emails. That's the one manual, non-code prerequisite blocking any implementation — nothing else can start until that credential exists.
