## Problem Statement
A real, operating laundry business currently tracks orders by phone/paper/spreadsheet. There is no app yet. The owner has already built a complete, working front-end prototype (`lavanderia-demo-v5.html`, single file, 1,527 lines, localStorage as fake DB) that fully specifies the product: client ordering + tracking, staff order pipeline management, admin product/pricing/reporting, bilingual EN/IS, simulated email notifications. The task is not "design a new product" — it's "take this working spec to a real, deployed, production system for one shop."

## Status Quo
Order intake and tracking today: phone, paper, or spreadsheets (per user, this is the first real system for the shop). The prototype already encodes the target workflow in detail: order lifecycle (queued → accepted → in progress → ready → delivered), urgent/delivery/pickup modifiers, per-item pricing with a "price pending" state for custom items, and a full staff/admin back office.

## Target User & Narrowest Wedge
Three real roles, already defined in the prototype:
- **Client** — places orders, tracks status, sees pricing.
- **Staff** — runs the day's queue, advances order status, flags/resolves issues, logs manual/contract orders.
- **Admin** — owner — manages products/pricing, views reports (sales, customers, top services, revenue by category, turnaround time), manages client accounts.

Scale: 1 shop, <30 orders/day. No multi-location/contract-chain complexity needed yet (though the prototype already models a contract client — "Hótel Húsavík" — so that data shape is free to keep).

## Constraints
- Single shop, low volume (<30 orders/day) — infrastructure must stay simple and cheap, not engineered for scale it doesn't have yet.
- No online payment at launch — clients pay in person/cash/card outside the app. No PCI scope.
- Must replace localStorage with a real, persistent, secure database and real authentication (hashed passwords) — non-negotiable for a production app handling real client data.
- Real transactional email must replace the simulated "Emails" tab (order confirmation, status-change notifications) — bilingual (EN/IS), matching the existing copy already written in the prototype's `I18N` object.
- Reuse existing UX/business logic as-is wherever possible — it is complete, considered, and bilingual. Do not redesign the UI from scratch.
- User asked to use the gstack workflow/tooling for this project going forward (planning reviews, `/ship`, `/land-and-deploy`, etc.).

## Premises
1. The HTML prototype is the functional spec for v1 — same roles, screens, and business rules, rebuilt on real infrastructure. **Agreed.**
2. Single shop, low volume → simple infra is correct; do not over-engineer for scale that doesn't exist yet. **Agreed.**
3. Real email via a transactional API (e.g. Resend) triggered directly by backend/DB events — no workflow engine (N8N) needed at this size, despite the prototype's copy mentioning it as a future note. **Agreed.**
4. Production means real hashed-password auth and a real database, replacing localStorage — required even at small scale. **Agreed.**

## Approaches Considered

### Approach A: Rewrite in Next.js + Postgres
Port the vanilla-JS `render()` functions into React components; add a Postgres-backed API, real auth, real email.
- Effort: M — Risk: Low
- Pros: Mainstream stack, wide ecosystem/hiring support, clean separation of concerns.
- Cons: Rewriting working UI logic in React is real, non-essential work at this stage; more moving parts than a 1-shop app needs.
- Reuses: CSS, copy/i18n strings, business logic (pricing, status pipeline), data model.

### Approach B: Full custom backend (ideal long-term architecture)
TypeScript backend (Express/Fastify + Prisma + Postgres), React frontend, JWT + bcrypt auth, Resend for email, GitHub Actions CI/CD, staging + prod environments.
- Effort: L — Risk: Low-Medium
- Pros: Most maintainable/testable long-term; ready for payments, multi-location, or reselling to other laundries later.
- Cons: Slowest to first deploy; overkill for the current single-shop, low-volume scope; more infrastructure to operate day to day.
- Reuses: Data model, business rules, i18n content — UI still gets rewritten.

### Approach C: Supabase-backed, keep the existing file (chosen)
Keep the HTML/CSS/JS almost as-is. Replace `localStorage` calls with the Supabase JS client (Postgres + Auth + Row Level Security). A Supabase Edge Function fires on order-insert / status-change DB triggers and calls Resend to send real bilingual emails. No custom backend server to run.
- Effort: S (human: ~3-5 days / CC: ~1-2 hrs focused work), but the RLS policy design/testing and the localStorage→async-Supabase-client port are the two sub-tasks most likely to eat that estimate — call this out explicitly in `/plan-eng-review` rather than treating the whole port as mechanical. The current `render()` functions read state synchronously; swapping in Supabase calls means introducing async/await (or promise chains) through the render path, which is a real refactor, not a find-and-replace. — Risk: Low
- Pros: Reuses ~90% of the existing file (CSS, copy, pricing logic, pipeline UI); real auth + real database + real email with minimal new code; free tier comfortably covers this volume at <30 orders/day (see Open Questions for the actual limits).
- Cons: Vendor lock-in to Supabase-specific features (Auth, RLS, Edge Functions — Postgres itself stays portable); RLS policies must be written carefully so clients can only ever read their own orders, staff/admin can read everyone's, with dedicated test cases per role.
- Reuses: Nearly everything — HTML structure, CSS, i18n, pricing/business logic, UI copy.
- **Stretch goal, not v1:** Supabase Realtime could later upgrade the pipeline UI from poll/refresh to live push updates. This is a scope addition beyond "port as-is" — explicitly deferred to a fast-follow after launch, not part of the initial success criteria.

## Recommended Approach
**Approach C.** For one real shop that needs to ship fast, this converts a complete working prototype into a live production app with the least new code and the lowest cost, while keeping the underlying data in standard Postgres (so a later migration off Supabase, if the business ever grows into a multi-tenant SaaS product, stays possible).

## Open Questions
- Domain name and business email sending domain (needed to configure Resend + DNS/SPF/DKIM).
- Exact hosting budget ceiling — Supabase free tier covers 500MB DB + 50k monthly active users + 500k Edge Function invocations, and Resend's free tier covers 3,000 emails/month, 100/day; at <30 orders/day (≤2 emails/order ≈ 60/day, ~1,800/month) both stay well under free-tier limits, but confirm before committing since real usage (staff notes, issue flags) may add more email sends than modeled here.
- **Resolved for v1:** manual/contract-client order logging (the "Hótel Húsavík" flow) ships in v1 — it's already fully modeled in the prototype's data structures and staff UI, so excluding it would mean rebuilding staff-facing screens twice. No separate open question; it's in scope.
- Backup/export policy for order history (Supabase has point-in-time recovery on paid tiers only — v1 relies on daily logical backups via `pg_dump` until/unless the owner upgrades).
- Data migration: existing localStorage demo/seed data (client accounts, order history) is NOT migrated — it's sample data for the prototype only. Production launches with an empty database; the first real admin account is created via a one-time Supabase SQL seed or the Supabase dashboard (not through the app's signup form, since staff/admin signup isn't a client-facing flow).
- Staff/admin provisioning: admin accounts are created manually (SQL seed or Supabase dashboard) at launch; the admin then invites staff accounts from within the app (staff do not self-register), mirroring the prototype's role separation.
- Password reset: use Supabase Auth's built-in magic-link/reset-password flow for all three roles — in scope for v1, not custom-built.
- Email failure handling: order creation and status changes are NEVER blocked on email send succeeding — the Edge Function fires fire-and-forget after the DB write commits, and failures are logged to the existing `emailLog` table with a `failed` status rather than retried automatically in v1. Resend delivery/bounce webhooks are deferred to a fast-follow, not v1.

## Success Criteria
- Real clients can register, log in, place orders, and see live status — no localStorage, no demo data, on a real domain.
- Staff can run the daily queue and advance orders through the pipeline from any device, including logging manual/contract-client orders.
- Admin can manage products/pricing and see accurate reports pulled from real order data.
- Order confirmation and status-change emails are actually delivered to real inboxes, bilingually, without ever blocking the underlying order action if email send fails.
- Passwords are hashed (via Supabase Auth); a client cannot read another client's orders, and this is verified with explicit RLS policy test cases per role (client/staff/admin) before launch.
