## Locked decisions (from this review)

1. Order line items are a normalized `order_items` table, not JSONB on `orders` — needed for admin reports (revenue by category, top services) without unnesting JSON.
2. Staff/admin are Supabase Auth users via one `profiles` table with a `role` enum, same identity system as clients — no parallel auth.
3. Status-change emails fire from a Postgres `AFTER UPDATE` trigger that diffs `OLD.estado` vs `NEW.estado` — not a naive Database Webhook on every UPDATE (which would spam clients on note/price edits).
4. Staff writes to orders go through security-definer RPC functions (`advance_order_status`, `add_order_note`, `flag_problem`), not direct table UPDATE — DB-level blast-radius control if a staff session is ever compromised.
5. `settings` is a single-row table enforced by a `CHECK (id = 1)` constraint — a second row is a constraint violation, not an app-level assumption.
6. The async/sync mismatch (Supabase is async, `render()` is sync) is bridged by keeping the existing in-memory `db` cache: mutate via Supabase → refetch the changed slice → call `render()` unchanged. render() functions are not rewritten.
7. Failed writes show the existing `toast()` pattern with a clear, localized error; local state and open forms are left untouched (no silent optimistic rollback).
8. Client email language is persisted (`profiles.preferred_lang`, default `'is'`) — the in-page EN/IS toggle is a browsing preference only, not the email-delivery language.
9. Admin reports stay client-side JS aggregation over fetched rows (matches the prototype's existing `reduce()`-based functions almost verbatim) — SQL aggregation is explicitly deferred until order volume actually demands it.
10. A `handle_new_user`-style `AFTER INSERT` trigger on `auth.users` creates the matching `profiles` row (role='client', preferred_lang='is') at signup time — without it, RLS checks that join on `profiles.role` would silently break for every new account.
11. `profiles.role` and `profiles.is_contract` are protected from client self-escalation by a `BEFORE UPDATE` trigger checking `OLD.role = NEW.role AND OLD.is_contract = NEW.is_contract` for non-admin callers — RLS alone is row-level only and cannot restrict individual columns.
12. Trigger→Edge Function calls use `pg_net`'s async HTTP queue (not the synchronous `http` extension) — this is what actually makes "order write never blocked by email" true, since `pg_net` queues the request and returns immediately instead of holding the transaction open.
13. Staff/admin Today/Orders views poll every 20s while the tab is open (no Supabase Realtime in v1) — a simple `setInterval` refetch, not a manual-refresh-only UX.
14. `notify_price_assigned` batches per order, not per line item — an admin assigning prices to multiple pending items on one order triggers a single "items priced" email once the order has no more pending items to price, not one email per item.
15. Automated daily `pg_dump` backups are in v1 launch scope (e.g. via a scheduled GitHub Action), not deferred — a live revenue business cannot launch with zero backup posture, even on the free tier.
16. Launch uses a separate staging Supabase project plus a documented cutover checklist (final data check, DNS/domain switch, first-real-order smoke test) and a rollback note (temporary revert to phone/paper if launch fails).

## Schema

```
profiles
  id              uuid PK, references auth.users(id)
  role            text CHECK IN ('client','staff','admin')
  name            text
  phone           text
  email           text
  is_contract     boolean DEFAULT false
  notifications_enabled boolean DEFAULT true
  preferred_lang  text CHECK IN ('en','is') DEFAULT 'is'
  registered_at   timestamptz DEFAULT now()

products
  id              text PK        -- matches prototype's "key" (e.g. 'bedsheets')
  name_en         text
  name_is         text
  price           numeric NULL   -- null = price-pending item (e.g. "other")
  unit            text CHECK IN ('pc','kg','set')
  category        text CHECK IN ('bedding','apparel','general','other')
  active          boolean DEFAULT true
  sort_order      int

settings
  id              int PK DEFAULT 1, CHECK (id = 1)   -- singleton
  express_percent numeric
  delivery_fee    numeric
  pickup_fee      numeric
  discount_percent numeric
  delivery_enabled boolean
  pickup_enabled  boolean

orders
  id              text PK        -- e.g. "ORD-1042"
  client_id       uuid NULL, references profiles(id)   -- null only for pure walk-in w/o account
  client_name     text           -- denormalized display name
  fecha           date           -- requested delivery date
  comentarios     text
  estado          text CHECK IN ('en-cola','aceptado','en-proceso','listo','entregado')
  urgent          boolean
  return_method   text CHECK IN ('store','delivery')
  pickup          boolean
  problem         boolean DEFAULT false
  source          text CHECK IN ('client','staff')
  notas           jsonb          -- array of note codes/text, not aggregated in reports — jsonb is fine here
  created_at      timestamptz DEFAULT now()
  delivered_at    timestamptz NULL

order_items
  id              uuid PK DEFAULT gen_random_uuid()
  order_id        references orders(id) ON DELETE CASCADE
  product_id      references products(id) ON DELETE RESTRICT
  qty             numeric
  price_override  numeric NULL   -- admin-assigned quote for "other" items
  desc            text NULL

email_log
  id              uuid PK DEFAULT gen_random_uuid()
  order_id        references orders(id) NULL
  to_address      text
  subject         text
  body            text
  status          text CHECK IN ('sent','failed')
  sent_at         timestamptz DEFAULT now()
```

## RPCs (security definer, staff/admin only)

- `advance_order_status(order_id)` — server computes the next state from `ESTADOS` order; staff/client cannot set an arbitrary state, only "advance one step."
- `add_order_note(order_id, note)`
- `flag_problem(order_id, flagged boolean)`
- `assign_item_price(order_item_id, price)` — admin only
- `log_manual_order(...)` — staff, inserts with `source='staff'` (walk-in / contract-client flow, e.g. "Hótel Húsavík")
- `handle_new_user()` — trigger function on `auth.users` `AFTER INSERT`, inserts the corresponding `profiles` row

Every function above is `SECURITY DEFINER` and MUST pin `SET search_path = public, pg_temp` in its definition — unpinned search_path on a security-definer function is a schema-injection privilege-escalation vector.

A separate `BEFORE UPDATE` trigger on `profiles` (not a SECURITY DEFINER RPC) rejects any client-initiated change to `role` or `is_contract`, since RLS cannot restrict individual columns.

## Triggers → Edge Function → Resend

```
auth.users AFTER INSERT
  └─▶ handle_new_user ──▶ inserts profiles row (role='client', preferred_lang='is')

orders AFTER INSERT
  └─▶ notify_order_created  ──▶ pg_net.http_post (async queue) ──▶ Edge Function ──▶ Resend (confirmation email, preferred_lang)

orders AFTER UPDATE
  └─▶ IF OLD.estado IS DISTINCT FROM NEW.estado
        └─▶ notify_status_changed ──▶ pg_net.http_post (async queue) ──▶ Edge Function ──▶ Resend (status email, preferred_lang)
      ELSE: no email (comentarios/problem/notas edits do not fire)

order_items AFTER UPDATE
  └─▶ IF OLD.price_override IS NULL AND NEW.price_override IS NOT NULL
        AND no other order_items on this order still have price_override IS NULL
        └─▶ notify_price_assigned ──▶ pg_net.http_post (async queue) ──▶ Edge Function ──▶ Resend (one quote-confirmed email per order, not per item)
```

All three use `pg_net`'s async HTTP queue, not the synchronous `http` extension — `pg_net` enqueues the request and returns immediately, so the trigger's own `AFTER` transaction commits without waiting on Resend/the Edge Function. This is what actually makes "fire-and-forget" true: an `AFTER` trigger runs inside the same transaction as the write, so a *synchronous* HTTP call would add latency to (or fail alongside) the order write itself. On Edge Function/Resend failure: insert an `email_log` row with `status='failed'`; the order/status/price write itself is never rolled back or blocked. No auto-retry in v1 (Resend webhooks deferred, per design doc); failed rows are surfaced in an admin-facing view (see Implementation Tasks, T8).

## RLS summary

| Table | client | staff | admin |
|---|---|---|---|
| profiles | select/update own row (RLS); `role`/`is_contract` additionally guarded by a `BEFORE UPDATE` trigger, since RLS is row-level and cannot restrict individual columns | select all | select/update all incl. role |
| products | select where active=true | select all | select/insert/update (delete blocked by FK if referenced) |
| settings | select | select | select/update (insert/delete blocked — seeded once) |
| orders | select/insert where client_id=auth.uid() | select all; insert (source='staff'); NO direct update; polls every 20s for new/changed rows (no Realtime in v1) | select/insert/update all; same 20s poll |
| order_items | select via parent order | select all; write only via RPC | select/write all |
| email_log | — | select | select/insert; failed rows surfaced via an admin-facing filtered view (T8) |

RLS test cases (one per role × table, allowed + denied) are the project's explicit launch success criterion — see Test Plan artifact `arnoldoarguello-noeol-eng-review-test-plan-20260709-234933.md`. The `profiles.role`/`is_contract` column protection is tested separately as a trigger test, not an RLS test, since RLS cannot express it.

## NOT in scope (explicitly deferred)

- **Online payment / PCI** — no online payment at launch (design doc constraint).
- **Supabase Realtime push updates** — stretch goal, fast-follow after launch, not v1.
- **Resend bounce/delivery webhooks** — email failures are logged, not auto-retried; webhooks deferred.
- **SQL-based report aggregation** — client-side JS aggregation is correct at <30 orders/day; revisit if volume grows by orders of magnitude.
- **Automatic email retry on failure** — logged to `email_log` as `failed`, no retry loop in v1.
- **Formal multi-location entity modeling for contract clients** — "Hótel Húsavík" stays a single profile with a free-text order-level location field, matching the prototype's own (non-structural) handling.
- **Point-in-time recovery / paid Supabase backups** — v1 relies on automated daily `pg_dump` (now in launch scope, see decision #15) until the business upgrades tiers; PITR itself stays deferred.

## Failure modes

| Codepath | Realistic failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| Order insert | Network drop mid-submit | Planned (Test Plan) | toast() + form untouched | Clear error, can retry |
| Status-change trigger | Edge Function/Resend down | Planned | email_log status='failed', order write unaffected | Order still advances; no email sent (silent to client, surfaced to admin via T8 failed-email view) |
| Signup | Profile-provisioning trigger fails/is missing | Planned | handle_new_user trigger tested at T1; without it, RLS checks joining profiles.role break for the new account | Blocked launch-readiness issue if trigger test fails, not a silent runtime gap |
| Backup | Supabase project lost/corrupted with no PITR (free tier) | Planned | automated daily pg_dump (decision #15) restores to a known-good point within 24h | Worst case: up to 24h of order data re-entered manually from paper/phone fallback |
| RLS boundary | Compromised client session queries another client's orders | Planned | RLS denies at DB level | Empty result, no data leak |
| Staff direct UPDATE attempt | Bypasses RPC via raw Supabase client call | Planned | RLS denies (no direct UPDATE grant) | Error surfaced to staff UI as a failed write |
| Settings second row | Race condition / bad migration script | Planned | CHECK constraint violation | Insert fails at DB level, no silent duplicate |
| Product delete while referenced | Admin deletes an in-use product | Planned | FK RESTRICT — app catches and shows "cannot_delete_used" copy | Friendly error, not raw DB exception |

No critical gap identified without both a planned test and DB-level error handling — the "silent + untested" case that would warrant a hard block did not occur in this design.

## Worktree parallelization strategy

Sequential implementation for the first pass — no repo or codebase exists yet, so there is no independent module boundary to split across worktrees until the schema/migrations land first. Lane B (the HTML/JS port) is corrected from the original draft: it needs Lane A's schema, RLS, *and* RPCs actually implemented (not just interface-named) to be verifiable, since the port's code both calls the RPCs directly and depends on RLS actually allowing/denying the right rows during testing. Only Lane C (Edge Function + Resend) is genuinely interface-only parallel with B.

| Step | Modules touched | Depends on |
|---|---|---|
| A1: Schema migrations (tables, triggers, singleton constraint) | `supabase/migrations/` | — |
| A2: RLS policies | `supabase/migrations/` | A1 |
| A3: RPCs (security-definer functions) | `supabase/migrations/` | A1 |
| B: Port HTML/JS to Supabase client calls | root HTML file | A1 + A2 + A3 all implemented (not just named) |
| C: Edge Function + Resend integration | `supabase/functions/` | A1 (needs trigger/table names only — genuinely interface-only) |

A1, A2, A3 land sequentially first (all three, not just A1). C can start in its own worktree as soon as A1's interface is fixed, in parallel with A2/A3. B cannot meaningfully start (or at least cannot be tested/verified) until A1+A2+A3 are all done. Merge C once ready; merge B last, once A2/A3 land.
