## Affected Pages/Routes
- Client auth (signup/login/reset) — first real auth surface, replaces demo phone/pass with Supabase Auth
- Client order sheet (new order) — writes orders + order_items, must trigger confirmation email
- Client order tracking (active/history) — RLS must scope to own orders only
- Staff Today/Orders/Clients/Reports — RLS must allow read-all but block direct order UPDATE (RPC-only)
- Staff manual/contract order logging (e.g. "Hótel Húsavík") — source='staff' path
- Admin Products/Pricing/Quotes/Reports — full read/write, settings singleton enforcement

## Key Interactions to Verify
- Client submits new order with a mix of priced items and one "Other" (price-pending) item
- Staff advances an order through the full pipeline (en-cola → aceptado → en-proceso → listo → entregado)
- Staff edits a note or flags a problem WITHOUT advancing status
- Admin assigns a price to a pending "Other" item
- Admin edits settings (express %, fees, discount) and attempts a second settings row (should fail)
- Admin attempts to delete a product that is referenced by existing orders (should be blocked with a friendly error)

## Edge Cases
- Client A attempts to read Client B's orders directly via the Supabase client (must be denied by RLS)
- Staff session attempts a direct UPDATE on orders.price/items columns instead of going through the RPC (must be denied)
- Non-admin attempts to UPDATE the settings row (must be denied)
- Order status updated but estado unchanged (e.g. editing comentarios) — must NOT fire a status-change email
- Resend API failure during order creation — order must still save; email_log row gets status='failed'; order flow is never blocked
- Rapid double-advance of the same order's status (two staff clicks) — exactly one status-change email, no duplicate

## Critical Paths
- End-to-end: client signs up → places order → receives confirmation email in their preferred_lang → staff advances status → client receives status-change email → staff marks delivered
- End-to-end: staff logs a manual contract order (Hótel Húsavík) with a price-pending item → admin assigns price → client (if notifications enabled) is notified
- RLS boundary suite: one test per role (client/staff/admin) × one test per table (profiles/products/orders/order_items/settings/email_log) confirming allowed and denied operations — this is the project's explicit launch success criterion
